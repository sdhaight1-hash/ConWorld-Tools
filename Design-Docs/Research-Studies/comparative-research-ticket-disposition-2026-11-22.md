## Proposal A — Architectural Evolution: Independent Editorial Draft and Publication Lifecycle

**Proposed / high priority, conditional on owner demonstrating need for staged editing.**

Problem and baseline: study §9.4, §9.7; store/entries.rs save_entry_layout writes document and published flag together, replaces public index/captions/dependencies and entry links transactionally; read_layout_at resolves latest eligible layout; workspace_save_layout returns unit; entry-editor.ts save sends checkbox, expected revision. A published page edited and saved while checked becomes the new publication. Saving unpublished withdraws current reader access. No separate currently released version survives unpublished work on same entry through this path. This is current behavior, not proven corrupt data. Normative 06 §§1,6–8 demands authorized versions/compiler, autosave and separate representation; 08 lists edit_canvas and publish_entry commands; ADR-010 edit/merge policy for published/derived records is open. A clearer pair of existing save/publish/withdraw actions is routine #5/#8/#10 work and MUST happen first. Only the new dual-head coexistence and changed publication/head-selection semantics require evolution approval. If existing contracts and explicit actions meet actual owner workflow, retain them and withdraw proposal.

Proposed delta: separately identify immutable latest author draft version and explicit current release selection, **for the same single entry and world store**. Author edits/save/restore append history, do not silently change current release. Publish explicitly validates draft/layout, current policy, same world, revision and selected supported context and atomically updates release/index; withdrawal revokes release independently. Current reader gets authorized current release, not latest draft by accident. Prior release content may have dynamic typed components evaluated at selected fictional date under existing scoped policy; exact time/pin contract must be reconciled with 06, INV-13/15 and #8, do not promise that authored prose is automatically historical. Revocation still authoritative even when viewing old versions; restoration of draft cannot revive revoked grants. Current main-only implementation retained until existing branch/perspective gates support widening. No extra ontology type, reader privileges, editorial approval roles, generalized workflow engine, cloud, collaboration, auto-publish or historical release time-travel. Archived or previously exported reader artifacts cannot be remotely recalled.

Before/after:
- Current single newest layout with publication flag; explicit release change coupled to save.
- Proposal latest authored layout separate from current release pointer/event. Same compiler, version IDs and authoritative Rust transactions; current release may lag draft.
- A save result returns committed version/context and generation; frontend marks only matching draft clean, no stale reply overwrites.

Ownership and dependencies: #5 Canvas/Display (layout/persistence/author commands), #8 policy and current release selection, #4 search/backlinks/anchor reauthorization, #10 archive/recovery/offline native test. #75 exact-head consolidation and review precede migration. #72 unchanged. Reconcile 06 §§1/6/7/8, 08 edit/publish and persisted layout API, 07 publication dependency model and ADR-004/005/010. Existing AT-17/18/19/20/22/25/34 unchanged. Scope proposal only, no new normative text yet.

Alternatives: retain combined current state with honest Save unpublished (withdraws) / Save and publish; or explicit host-level draft UI without durable staging (doesn't meet saved-edit/reopen scenario). Do not add separate database or copy canonical data. Need real native author task demonstrating continued reader access while revised author page is saved/reopened. Independent editing of released article adds publication/index migration burden; no implementation unless value established and owner accepts specific delta.

Migration/compatibility: pin accepted baseline, examine latest layout per entry. Proposed backfill release to same existing latest published version only if currently published, otherwise none; never select a previously published but now withdrawn layout. Stable ObjectId/ElementId, layout/template pins, provenance, branch history, archive hashes. Transactional migration and verified pre-migration protected backup; check old schema refusal, rollback on failure, restore exact prior archive; rebuild publication indices exclusively from current release selection, no draft leakage. Exact schema/table design and handling legacy revisions/invalid pointers to be reviewed, not fixed here.

## Proposal B — New Feature: Configurable World Management Workspaces and Dashboards

**Proposed / high author value, after core shell and saved queries.**

Problem: authors undertaking contrasting tasks (genealogy, geopolitical history, article writing, place research) repeatedly locate their working records, filters and views. The accepted roadmap already promises Node/Canvas/Display, saved queries, layout primitives, templates, selection/navigation context and bound components; those are NOT the new feature. Proposed additional behavior: durable named, per-world, **author-only task workspaces**, reusable dashboard configuration across sessions, retaining a collection of compatible view references, author tools and contextual focus. Unlike an ordinary article Canvas, dashboard belongs to a user's world-management workflow rather than a semantic entity/public page. Unlike #70 recipes, dashboard panels display existing queries independently; no sequential workflow composition. Unlike #72 classification, it is presentation metadata only. If fixed explorer, existing saved queries and a regular Canvas page solve the author tasks, do not build it.

V1 behavior: start with default fixed workspace and at most a small bounded user-defined number of named workspaces per world (suggest 8, max 8 panels each for spike; validate actual limits during design). Choose an existing saved-query pin or compatible already implemented domain view, optionally a permitted entry shortcut, compact list/table, arrange small grid/stack, toggle panel visibility, rename, remove and restore default. Saved view options distinguish current shared historical context vs explicitly supported pinned context; never silently mix. Standard task presets e.g. dynasty management, institution history, article authoring can be built from supported views, not hardcoded new modules. No saved canonical rows or author content duplicated in configuration; no custom widgets/code/formulas, arbitrary docking, new query AST, cloud synchronization, collaboration, public dashboard publishing, cross-world links, automatic facts, simulation or unapproved new domain editor. Sidebar exploration and ordinary contextual panels stay #4/#5.

Architecture: minimum local author workspace preferences/config, exact stable query/entry references and version pins, validate at load, deletion removes configuration only. Decide per-world author settings persistence vs portable world metadata explicitly (if archived, distinct optional author-only section, validate restore and never expose via reader). No new ObjectKind, ontology or fourth entry layer. Rust resolves each supported reference with existing authorized service and context, no authority through layout; shared cancellation and aggregate refresh budget, lazy focused panel reads, context generation guards; author-only unavailable panel explains missing pin/capability without silently broadening query. UI first standard DOM and reusable panel components, no wgpu requirement. Separate view presentation from query definition; no raw SQL/JS. Reuse fixed shell/typed query helpers so single query remains valid without dashboard.

Dependencies: #75/#72 review; #4 complete shared query/pagination/typed selectors; #5 workbench/dirty guard/basic author panels; #8 validated context; #10 preferences/archive decision. #6/#7/#68 domain widgets only after respective service acceptance; #70 WT-01 unchanged. Existing GUI shell fixes never delayed by this proposal. After owner acceptance, write scoped specification in Design-Docs/Features, cross-link owners. No feature spec registered before acceptance.

Readiness alternatives: compare fixed explorer + saved query links, ordinary authored Canvas page, and dashboard on same actual world and historical context. Example dynasty task: open house record, list currently accepted family members, inspect sourced title succession and open relevant article, change fictional date and return to saved view. Repeat for institution and research/writing workflow. Compare actual actions/time/context switches, errors, reopens, first useful view. Demonstrate reduced repeated navigation or reproducible organizing benefit; stop if ordinary views suffice. No invented timings or competitor usability statistics.

Proposed gates (not passed):
- [ ] B1: owner approves bounded author-only scope; native baseline comparison demonstrates specific improvement, validated fixture and declared budgets; otherwise defer.
- [ ] B2: create two task workspaces, arrange supported panels, reopen app, switch selected day/branch only where supported; same query identities and permissions as ordinary queries; explicit stale/unavailable result, preserved context and dirty draft.
- [ ] B3: delete/rearrange/rename workspace without canonical mutation; no cross-world leakage; query pin/version invalidation, settings restore/default, archive behavior verified if chosen. No public exposure of configuration/author payload.
- [ ] B4: keyboard and screen-reader interaction, 460x540,1080x760,1920x1080 and 200% zoom, offline/no GPU; bounded number of simultaneous queries/cancellations at 1k/10k/50k, no unbounded fanout or duplicate service. Measure time/bytes/memory and actual task counts against plain search.
- [ ] B5: native Linux/Windows, screenshots of actual running fixture, documentation and owner review; no phase gates redefined.

## Additional possible proposals — defer, don't open

1. **New Feature: Reusable Linked Content Sections (transclusion)**. General cross-entry shared authored blocks outside explicit link and existing dynamic data bindings; no reviewable production claim. Need real repeated authoring cases where links, template snapshots and existing typed queries do not meet need, dependency/recursion/fanout limits, host/target intersection, current revocation, hidden-budget noninterference, stable IDs and archive/export. Study §9.5 synthetic tests are not enough; prefer precise anchors first.
2. **New Feature: Selective Cross-World Content and Template Interchange**. World archive import/export existing #10; multi-world shared library or selective cross-world transfer of canonical records is genuinely extra, requires explicit identity mapping and provenance, no cross-world implicit refs, asset/license/pin validation and transaction/rollback. Need actual owner task, not proposed for immediate work.
3. **New Feature: Curated Knowledge Collections and Reading Trails**. Only if author-authored reusable multi-parent collections with ordering, entry-independent publication and independently curated navigation cannot be realized by existing Canvas pages/saved views. First support directory, ordinary links, saved queries and authored homepages. Avoid conflating folder with Place, collection with canonical classification, hierarchy with relation. No new schema until demonstrated.
4. **Reject/defer** general formulas, EAV schema builder, plugin/script execution, collaboration/cloud licensing services, arbitrary sync runtime, freeform board default, session scheduler and full manuscript tool. Existing product charter and #72/#70 stop rules apply.
