**Status:** In Review — comparative research and isolated experiments completed; owner decision and architecture handoff remain pending.

**Decision sought:** Does a Transform abstraction improve world creation and historical exploration enough to justify new scope? No production changes, feature approval, roadmap changes or new dependency authorized by this study.

## 1. Conclusion and scope

Recommend contextual Explore actions first on existing QuerySpec and typed domain services (#4/#5); do not build a second query engine. A small typed operation catalog might justify separate feature scope only for reusable multi-input/step recipes, inspectable intermediate provenance and author-driven world-consistency/source-review workflows beyond existing query bindings. Validate the author workflow before committing to generalized recipes. Do not build a Maltego clone or a workflow scripting language. Existing ancestry, event causality, affiliation, search, mention review and maps remain existing domain obligations; the Transform is their discoverable entry point, not a new kind of historical fact.

Fictional-world authoring is the criterion: easier creation of coherent lore, navigating historical worlds, comparing family branches, noticing unfinished connections and reviewing candidate content. No live OSINT, real-person investigation, external provider harvesting, autonomous exploration, or investigative case management. Optional imported manuscripts, family trees and setting notes are authored fictional source material. No requirement for network, AI or third-party transforms. Borrow principles, not private source code or research data.

## 3. Maltego: actual architecture and applicable ideas

Legacy Transform documentation [R1] emphasizes small related-entity operations and composition, with classic XML messages; [R3] describes local desktop executable/interpreter configuration and typed input metadata. Do not conflate offline executable integration with modern server integration. [R2] documents selected-entity-filtered searchable menus, execution progress and cancellation. These are useful discoverability and control patterns for Node Studio.

Current documented SDK 1.0.0 [R4] recommends maltego-transforms instead of maltego-trx for new integrations; typed entity model, server runtime, authentication and pagination. [R5] distinguishes single, list and graph input, with list batch and graph semantics differing by client (graph input desktop only; browser runs list selection individually). Output can support graph linkage; not a guarantee of Atlas canonical semantics. [R6] Transform Sets are discovery groupings, not execution sequences. [R7] Machines are desktop workflow assets defined in a DSL that reference registered operations and dependencies. [R8] legacy TDS mediates configuration and requests/responses between desktop and service. Atlas does not need TDS, Hub, provider authentication or a new local HTTP server. No external SDK dependency selected.

Translate entity input to stable world-scoped ObjectRef, not label; returned "new entity" translates to existing authorized canonical ref, view-only derived path, candidate with provenance, or explicit reviewed command. Map Set to menu category, not auto-run; Machine to a bounded pinned typed recipe only if justified. Never model a historical relationship solely because an execution returned a node. Do not imitate arbitrary graph input where a typed pair or selection suffices.

## 6. Author workflows, comparison and priorities

Analytical task comparison: count logical user operations, not actual UI clicks or measured usability. Starting selected entity, already configured date/branch and existing definitions; a manual action = choose relevant query/predicate, bind identity/role and execute (three logical actions), context action = choose applicable operation and execute (two, possibly one if no prompt), recipe = choose preconfigured recipe and execute (two). Selection/disambiguation/parameters and review add work; a pinned saved query may already be equally fast. Compare on same semantics, not a deliberately awkward query UI.

| Fictional-world task | Existing/manual equivalent | Contextual adaptation | Added value / dependency |
|---|---|---|---|
| House Vale ancestry and rival claimant | Family links, type-specific ancestry and shortest/common ancestor queries; two ancestor projections and compare | Select one person "Biological ancestors"; select two "Common ancestors", evidence paths | One-input already within #4/#6. Pair workflow reduces context switches, not new genealogy math; bounded pair proof and uncertain/legal distinctions |
| Guild schism and historical consequences | ParticipantEvents, network facts, explicit confirmed impact; query each stage | Person→House→members→guilds→events, inspect each edge and date; separate causal effects action | Four manual stages ~12 logical operations, contextual ~8, curated recipe ~2 plus review and setup. Never infer selected person participated or caused outcome. Recipe gives repeatable path provenance. |
| Contradictory fictional treaty | Find source claim text; inspect matched names/aliases/evidence; compare two accounts, review ghost | Source→mentions, referenced claims and unresolved candidates; "Compare accounts" with two compatible claims, show discrepancy and source spans | Existing #4/#8 mention and claim semantics; new review batching/worklist only if author workflow demonstrably useful. No automatic factual contradiction detector without typed qualifiers. |
| Geography of contested succession | Select place, query residents/jurisdiction/ownership/event sites by date, view map | Place→residents→institutions→events; snapshot date compare; send authorized place IDs to map binding | #68 required, avoid duplicate spatial query or geometry generation; no membership from spatial proximity |
| Fill out an unfinished setting bible | Search, create identities, review source references manually | Local document review, missing references, inconsistent typed dates, optional candidate checklist | Potential net-new source review workflow; separate ingestion scope if beyond planned discovery. Unknowns shown as not established, not auto-generated canon. |

Additional useful catalog: Person→family, memberships, offices, event roles, residence only after #68; House→members/succession/assets; Organization→leadership, membership history, split/successor, holding; Event→participants/confirmed causes/effects vs alleged causes; Conflict→issue-specific parties/stances; Claim→support/contradiction links; Asset→ownership/succession; Place→within/located or map under #68; Population→documented migration and synthetic ancestry under #9. Cultural/religious developments and trade only use actual typed kinds, tags, organizations, claimed facts and evidence; don't invent new economic/culture subsystem because it sounds useful. Reuse author’s current timeline and source context. Potential consistency checks: explicitly overlapping exclusive offices, invalid chronology/typed relationships, dangling references, ambiguous alias, unresolved date, documented incompatible facts. Flag for review; deliberate disputed records remain valid claims.

Run `python check.py`. Python 3.13.5, SQLite 3.46.1, Linux 6.18.57 x86_64 glibc2.41, in-memory fixture, CPU only. Five small typed query adapters, frozen View, read-only SQLite query_only, indexed outgoing edge and shared filter, four-step chain; ordinary equivalent single SQL join uses same visibility/effective time/revision predicate. Synthetic IDs only. Branch fixture one fork pinned to revision 1, no withdrawal/overlay hierarchy. Scope fixture author/public boolean, no world ID/character permission or real Atlas access model. Record distinct original edges with source; dedup node/frontier and edge ID; candidate mentions are returned as candidate but excluded from factual frontier. All assertions passed:
- Public day10 returns event e; author returns e/e2 via secret household member, public day20 returns e2; day20 revision1 has no visible terminal events; fork revision2 retains ancestor rev1 and branch guild membership, excludes parent rev2 event -> e only. All five equal SQL distinct terminal result. Two distinct original sourced guild edges retained; terminal one ID.
- Same input repeat equality; wrong input kind, incompatible adjacent stages, hidden root and chaining candidate mention denied. Candidate status retained, no terminal promotion; no SQL writes (query_only and total_changes).
- Max_calls and edge cap mark partial and suppress terminal completeness; cooperative cancellation before executing returns cancelled. Secret intermediate not returned in public edges. This is fixture visibility behavior, not proof of no timing/count leaks, hidden-source noninterference or native security. No dynamic code, graph input, UI or persisted recipe.
- Sparse 1k/10k/50k unrelated background edges/people plus 11 fixed fact/candidate rows, four calls, five returned distinct edges, one public terminal. Fifteen measured repetitions per size; timings median independently, perf_counter_ns, includes Python/SQL overhead, excludes seeding, IPC/rendering, graph layout, archive and real dense traversal. Join returns terminal IDs only whereas chain returns intermediate evidence and terminal, so timings are not equivalent output work.

| Background rows | 4-step graph projection ms | Equivalent terminal join ms | Edges / calls |
|---:|---:|---:|---:|
| 1,000 | 0.042 | 0.014 | 5 / 4 |

Finding: no inherent query speedup from a composition wrapper. Sparse focused traversal remains cheap in this toy. A joined query is a good option when only final set needed; preserve intermediate links for review when author needs explanation. A chain can blow up on dense fanout; enforce global query/row/edge/depth/bytes/time budgets, batch frontier by type when measured, stop partial without false completeness. No latency SLA, no native benchmark, no visual study or screenshot, no full real Atlas query parity/branch tests, no historical ledger verification. Prototype has simplified direction-specific explicit fixture edges, no full inverse/interval semantics and no validation of arbitrary configuration. It is feasibility evidence only, not candidate production code.

## 8. Recommended minimal architecture and pseudocode (proposal only)

Use current typed queries and existing services as authoritative executors, one presentation graph. Avoid new canonical Transform object type and persistence until user need demonstrated. Initial context-action descriptor: stable operation identifier, display/category, input kind/arity, typed parameter schema, supported result shape and service binding, explicit capability. Existing saved query binding remains authority; a preset references it rather than stores separate query text. Server-side validates selection refs, view and budget; frontend never supplies arbitrary command names/SQL/script. Use native read-only service calls; require genuine path edges from authorized service, not infer relationship from returned rows. No implicit scope escalation.

~~~text
discover_actions(selection, view) -> allowed descriptors (metadata only)
run(action_id, selection_refs, typed_params, view, shared_control):
    validate version, input kinds/arity/world and actor capability
    pin view; resolve authorized inputs or deny
    dispatch existing validated QuerySpec/domain service
    validate result semantics and provenance, enforce caps
    return authorized fragment / rows / candidate report, status, context
    merge presentation by stable object/fact IDs; retain distinct evidence routes
    never write canon; explicitly invoke standard approved mutation if user chooses
~~~

If action result has candidate IDs, they cannot flow into canonical path traversal unless explicitly resolved/approved through existing write command and subsequent *new* snapshot. Derived edge/path labelled derived, stored fact ref distinct; do not collapse opposite directions or distinct assertions. Record date/branch/revision and purpose, preserve relation/role/lens/uncertainty. Graph union merge only same view; changing view cancels and clears/re-evaluates old graph rather than silently mixing history. Undo means remove discovery presentation, not discard canon. No hidden author result from stored graph re-render; reauthorize on each use, pin definitions rather than replicate facts, policy-mismatch invalidates. Public and character execution disabled initially because baseline QuerySpec author-only. Keep existing published components, never let client invoke author command with forged scope.

Possible separate approved feature: a reusable versioned Transform Recipe selects an allowed operation sequence with typed frontier, pinned inputs/versions and finite aggregate limits. Each step yields provenance and explicit complete/partial/error/cancelled; impossible type, wrong ref, missing dependency or failure diagnosed, don't continue on partial unless explicitly semantics supported. Start curated fixed finite recipes (one or two at most), no arbitrary loops, DAG designer, Python/JS plugins, remote service or automatic all-neighbor crawling. Recipe metadata may reference existing saved query pins; no persistence until replay/version/invalidation tested. Optional replayable author workbench only if user explicitly needs saved definitions/pinned context. Immutable results must be reauthorized and clearly historical, not current; default re-execution safer. Existing authorized Canvas bindings should use QuerySpec, not execute hidden recipes with author permissions. Map integration after #68 SP gates. Local lore extraction uses existing source and mention review first, separate proposal if import workbench extends original charter; no untrusted document instructions executed.

### Alternatives and stop conditions
A: existing queries unchanged, lowest cost but author must know where feature lives. B: small contextual presets and graph focus, low incremental cost, recommended first within #4/#5; no feature ticket for already planned neighbor expansion or query UI. C: shared typed registry plus bounded curated composition, medium cost (versioning, provenance, policy, cancellation, integration); only if B fails to satisfy repeatable multi-step author workflows, propose New Feature for recipe composition/workbench, not existing operations. D: independent runtime/plugins/DSL, high cost and duplicates authoritative query, rejected for v1. No need for external URLs, SDK or third-party provider. If three representative author workflows show no meaningful reduction in navigation/configuration or no improvement in explainability, stop at B. For candidate C require equivalent authorized results, preservation of original path and status, bounded execution, repeatable definition with appropriate version context and author review, and measured logically simpler workflow vs B (actual native task comparison if feature implemented). Do not claim numbers above are actual time savings.
