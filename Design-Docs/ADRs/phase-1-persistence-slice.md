# Phase One persistence baseline

**Scope:** [Phase One #2](https://github.com/sdhaight1-hash/ConWorld-Tools/issues/2), persistence foundation. [Phase Zero #1](https://github.com/sdhaight1-hash/ConWorld-Tools/issues/1) records the hosted Windows fallback and physical Windows acceleration results.

- **ADR-001, initial revision semantics.** A world starts at revision 0 on a stable root branch. A command appends one world-scoped revision and full object versions atomically. A read chooses the newest recorded version of each historical state at the requested author revision, then checks half-open valid intervals. `RecordState` appends a later state with an explicit start and shortens an overlapping predecessor in the same author transaction. `Correct` replaces the newest state and rejects overlaps with its predecessor. A correction can leave a gap if it moves the latest start forward. Earlier author revisions retain their original intervals.
- **ADR-001, pinned branches.** A fork uses an exact world day and pins the current parent author revision. Before the fork day the child reads that historical date from the pinned parent. At and after the fork, it inherits the parent's state active on the fork day, subject to that state's explicit expiration. Inherited events need an exact occurrence or a latest possible date on or before the fork. A child-local correction shadows an inherited state from the fork. Its first `RecordState` shadows from the explicit start day. Once shadowed, gaps remain gaps. Writes cannot set an interval before its branch boundary or introduce an occurrence that could predate the fork. Source references are checked against the writing branch and its pinned ancestry. Returned versions identify their source branch, and `branch_fork` exposes durable lineage. An event-anchored fork validates the exact occurrence in its parent at the nominated world day and pins that event version. Later corrections leave that anchor intact. Branch merging belongs to the later reconciliation contract.
- **ADR-003, initial time representation.** The store accepts signed, normalized world days and optional interval endpoints. Event occurrences may be exact, unknown or uncertain with labeled inclusive bounds. An occurrence's three-valued day match is independent of the record's half-open valid interval. Calendar registration appends a world-scoped rule version to the author ledger. Each version defines the world day of year zero, month one, day one, ordered month lengths, and an optional leap cycle that adds one day to one month on years divisible by the cycle length. Negative years use the same rule and year zero begins a cycle. Exact dates normalize to `WorldDay`. Month or year precision produces inclusive uncertainty bounds and preserves the author's label. Reverse conversion uses the same epoch and rules. Callers select a rule version by author revision, including a fork's pinned revision when appropriate. Changing rules leaves stored normalized event dates intact. Named eras map positive ordinals forward or backward from a signed year. An exact calendared occurrence keeps the calendar ID and revision, calendar coordinates, and original label. The store rejects a normalized day that disagrees with the pinned rules. Irregular leap exceptions and discontinuities are outside this rule set.
- **ADR-005, initial authorization boundary.** The facade is intended for the trusted local author process. Every record read takes an explicit world, branch, author revision, fictional day and scope. Public scope is denied before storage queries. Actor identities are audit metadata supplied by that process. IPC capabilities and perspective policies remain open.
- **ADR-006, migration and backup.** Bundle SQLite through rusqlite. Apply migrations and update `user_version` in one immediate transaction. Migration 0002 groups all preexisting corrections for each object and branch into its initial state. Only an explicit `RecordState` creates a later state. Migration 0003 adds fork metadata and per-object override boundaries without changing prior object versions. Migration 0004 adds calendar-rule versions and ordered months tied to the author ledger. Migration 0005 widens the object registry and adds typed claims, effects, fork anchors, calendared occurrences and eras. The registry rebuild verifies foreign keys before committing and restores enforcement before returning the store. A newer schema is refused. The migration introduces the first production tables for this repository. Earlier prototype databases require an explicit import path. Use SQLite's `VACUUM INTO` for a standalone database snapshot and require a new destination file.
- **ADR-007, initial registry.** Stable UUIDs carry their world. Registry kinds are closed in this slice, with checked, typed columns for event occurrences and source citations. Evidence references live on object revisions. Source references must resolve to an existing source in the same world and visible author lineage at the time of the command, including sources authored earlier in the same batch. Claims are independently versioned objects with a typed subject, a predicate, a statement and a required asserting source. They never rewrite their subject. A sourced event effect appends a new target state, pins the exact event and before/after versions, and fails the command if the event is unavailable, uncertain or later than the effect. A later state correction retains the original causal record. Actor-action links, relationship effects and public claim/knowledge projections belong to their respective roadmap phases.
- Commands use an expected world revision and a unique command UUID. An already committed UUID produces a distinct duplicate-command error. Failed batches roll back both the audit row and the invalidations. Derived readers can build from the committed invalidation records when they are introduced.
